## 0. 先に用語をかんたんに

ここで出てくる言葉を先にまとめておきます。分からなくなったらここに戻ってきてください。

| 用語 | ざっくりした意味 |
|------|------------------|
| **ハブ (Hub)** | ロボットの「脳」にあたる LEGO SPIKE Prime の本体。プログラムはこの中で動く。 |
| **Pybricks** | ハブの上で Python を動かすための仕組み。ハブ用の軽量 Python（MicroPython）。 |
| **MicroPython** | 小さなチップ向けの、機能を絞った Python。PC の普通の Python（CPython）とは別物。 |
| **CPython** | みんなが PC で使う普通の Python。ここでは「PC 側で動く Python」の意味。 |
| **BLE** | Bluetooth Low Energy（無線）。ケーブルなしで PC からハブへプログラムを送る。 |
| **pybricksdev** | PC 側のツール。書いた `.py` を BLE でハブに送って動かす。 |
| **F5** | VS Code で「実行」するショートカットキー。 |
| **ruff** | コードの「校正係」。書式を自動でそろえ（format）、おかしい所を指摘する（lint）。 |
| **venv (.venv)** | そのプロジェクト専用の「道具箱」フォルダ。ライブラリをここにまとめて入れる。 |
| **async / await** | 「待っている間に他のことも進められる」書き方（非同期処理）。 |
| **module（モジュール）** | 1 つの `.py` ファイルのこと。`import` で他のファイルから呼べる。 |
| **pre-commit フック** | `git commit` の直前に自動で走る仕組み。整形や記録の自動化に使う。 |

## 1. 全体像 — コードが動く場所は「2か所」ある

このプロジェクトで一番大事なポイントは、**コードが動く場所が 2 種類ある**ことです。
ここが分かると、あとは一気に読みやすくなります。

```
凡例:  ──▶ 処理の流れ      [PC] PCで動く      [ハブ] ロボットの中で動く

┌─────────────────────────── [PC] 側（普通のPython / .venv）───────────────────────┐
│                                                                                  │
│  VS Code ──F5──▶ launch.json ──(実行前の下準備)──▶ tasks.json で ruff を実行       │
│                       │                                                          │
│                       ├─(通常)   pybricksdev で .py をハブへ送る                  │
│                       └─(ログ付) run_with_log.py 経由で送る＋記録を残す           │
│                                                                                  │
│  git commit ──▶ pre-commit フック ──▶ changelog_hook.py が変更履歴を自動で書く    │
│                                                                                  │
└──────────────────────────────────────┬───────────────────────────────────────────┘
                                        │  BLE（無線）で .py を送って動かす
                                        ▼
┌──────────────────── [ハブ] 側（Pybricks の MicroPython）────────────────────────┐
│                                                                                  │
│   selector.py / run_*.py  ──import──▶  setup.py                                  │
│      （ロボットの動きを書く）           （準備＋便利な道具をまとめた土台）         │
│                                                                                  │
│   実際に動かす物: タイヤ(F/B)・アーム(E/A)のモーター、ボタン(C)のセンサー         │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- **ハブ側で動くコード**: `setup.py` / `selector.py` / `run_*.py`。
  `pybricksdev` がこれらをハブに送り、ハブの中の MicroPython が実行します。
  **PC では動きません。**
- **PC 側で動くコード**: `pybricksdev`（送るツール）、`run_with_log.py`（記録を残す道具）、
  `scripts/changelog_hook.py`（コミット時の自動記録）、`ruff`（整形・チェック）。
  **これらはハブには送られません。**

> なぜ区別が大事？ ハブ側は MicroPython なので、PC 用の便利ライブラリは使えません。
> 「このコードはどっちで動くのか」を意識すると、使える機能の範囲が分かります。

## 2. 動かしたとき、中で何が起きるか

ロボットの動かし方は 2 通りあります。それぞれ F5 を押したあとの流れを見てみましょう。

### 2.1 ふだんの開発: `run_*.py` を 1 つだけ動かす

ミッションを 1 つだけ何度も試したいときのやり方です。

```
F5（🤖 Robot N を選んだ状態）
  └─ 実行前の下準備（preLaunchTask "ruff: all"）
       ├─ 開いているファイルが .py か確認
       ├─ ruff format  … 書式を自動でそろえる
       └─ ruff check --fix … おかしい所を自動で直す
  └─ pybricksdev で、開いているファイルをハブに送って実行
       └─ ハブの中で、ファイル末尾の「直接実行されたときだけ動く部分」が走る:
            hub, robot, ... = initialize_robot()   # ロボットの準備
            run_task(run(...))                       # 自分の run() を動かす
```

各 `run_*.py` の末尾には `if __name__ == "__main__":` というブロックがあります。
これは「**このファイルを直接 F5 で実行したときだけ動く**」部分です。ここで
`setup.initialize_robot()` がロボットを準備し、自分が書いた `run()` を動かします。

### 2.2 本番・通し練習: `selector.py` を使う

複数のミッションを、ハブのボタンで選んで連続実行するやり方です。

```
F5（selector.py を開いた状態）
  └─ pybricksdev で selector.py をハブに送って実行
       └─ ハブの中で:
            initialize_robot()         # 準備は最初に1回だけ
            programs = [ ミッションの一覧 ]
            ボタンで選んで実行するループが始まる
                 │
                 ├─ ハブの左右ボタンで番号を選ぶ（画面に番号が出る）
                 ├─ フォースセンサー(C)を押すと、その番号のミッションを実行
                 │     実行の前後で reset_robot()（向きや距離をリセット）
                 └─ dev=True のときは、走りながらセンサーの値も表示する
```

`selector.py` は「複数ミッションをハブ単体で回す入口」です。`dev` という設定
（`selector.py:43`）を `True/False` で切り替えると、デバッグ表示の有無が変わります
（後述）。

## 3. ファイル同士の「お約束」— ここが連携の土台

このプロジェクトの部品がうまく噛み合うのは、**2 つの「お約束（決まりごと）」**を
全員が守っているからです。これさえ守れば、新しいミッションを簡単に足せます。

### 3.1 お約束①: 準備関数は「6 つの値」を返す

```python
hub, robot, left_wheel, right_wheel, left_lift, right_lift = initialize_robot()
```

`setup.initialize_robot()` は、いつでもこの **6 つ**（ハブ／ロボット本体／左タイヤ／
右タイヤ／左アーム／右アーム）をこの順番で返します。`run_*.py` も `selector.py` も、
この順番で受け取ります。

### 3.2 お約束②: ミッションは決まった形の `run()` を持つ

```python
async def run(hub, robot, left_wheel, right_wheel, left_lift, right_lift):
    # ここにロボットの動きを書く
    ...
```

- どのミッションのファイルも、この形の `run()` を必ず持ちます
  （`async` は「待っている間に他も動ける」書き方）。
- `selector.py` は、登録されたファイルから `run` を取り出し、同じ引数で呼び出します
  （`selector.py:216` 付近）。中身を知らなくても呼べるのがポイントです。

> このお約束のおかげで、新しいミッションは
> **「決まった形の `run()` を書いたファイルを作って、`selector.py` の一覧に足すだけ」**
> で組み込めます。`selector.py` 本体を書き換える必要はありません。

## 4. 土台になるファイル `setup.py`

すべての `run_*.py` が頼っている共通の土台です。役割ごとに小さな関数に分かれていて、
`initialize_robot()` がそれらを順番に呼び出します。

### 4.1 準備は 6 ステップで進む

| 順 | 関数 | やること |
|----|------|----------|
| 1 | `setup_hub()` | ハブの「上はどっち・前はどっち」を設定する |
| 2 | `setup_motors()` | タイヤ(F/B＝必須)とアーム(E/A＝任意)のモーターを用意する |
| 3 | `setup_robot_parameters()` | タイヤの大きさなどを設定し、後述の `Robot` で包む |
| 4 | `setup_pid_control()` | まっすぐ走るための自動調整（PID）を設定する |
| 5 | `initialize_sensors()` | 向きセンサーをONにして、向き・距離を 0 に戻す |
| 6 | `reset_motor_angles()` | 全モーターの回転角度を 0 に戻す |

### 4.2 `Robot` クラス — 使いやすくするための「包み」

Pybricks には `DriveBase`（2 輪走行をまとめて扱う部品）があります。`Robot` は、それを
**もっと使いやすく包み直したもの**（ラッパー）です。

- できること: `straight()`（直進）／`turn()`（その場回転）／`curve()`（カーブ）／
  `run_motor()`（モーター個別操作）。それぞれ呼ぶたびに速度などを指定できます。
- **速度は「一時的に変えて、使ったら元に戻す」**: 速度を指定したときだけ設定を書き換え、
  動作が終わったらデフォルトに戻します。次の動きに変な影響を残さないための工夫です。
- **時間制限（timeout）の仕組み**: Pybricks には「○秒で打ち切る」標準機能がありません。
  そこで「動作だけ先に始めて、ストップウォッチで時間を見張り、超えたら止める」という
  方法で実現しています（`setup.py:199-208` ほか）。
- デフォルト速度: 直進 400mm/s、回転 240deg/s、カーブ 240mm/s。

### 4.3 `NullMotor` — アームが無くても止まらない工夫

アーム用のポート **E / A にモーターが付いていなくても、プログラムが落ちない**ように
するための「ダミーのモーター」です。`_safe_motor()` が本物のモーター作成に失敗したら、
代わりにこの `NullMotor` を返します。

- 本物のモーターと同じ呼び出し方ができ、命令が来たら「すぐ完了した」ことにします。
- ただし **タイヤ(F / B)は必須**です。これが無いと走れないので、わざとエラーにします。
- 狙い: アームをまだ付けていない段階でも、走るプログラムを書き進められるようにするため。

### 4.4 数値の設定（ここを変えると影響が大きい）

| 項目 | 値 | いつ変える？ |
|------|----|--------------|
| ハブの向き | 上=Z軸 / 前=X軸 | ハブの取り付け向きを変えたとき |
| タイヤの直径 | 62 mm | タイヤを別のものに替えたとき |
| 左右タイヤの間隔 | 85 mm | 機体の幅（左右輪の間隔）を変えたとき |
| 距離の PID | kp=1000, ki=50, kd=10 | 進む距離が安定しないとき |
| 向きの PID | kp=2000, ki=50, kd=100 | まっすぐ／回転が安定しないとき |

> **PID とは？** ロボットを自動でまっすぐ・正確に動かすための調整機能です。
> P・I・D の 3 つの数値（ゲイン＝調整の強さ）で効き具合が決まります。
> 調整のやり方は [`how_to_reduce_SD.md`](./how_to_reduce_SD.md) にあります。
>
> `setup.py` は全ミッションが使う土台なので、ここを変えたら直線・四角・カーブの走行を
> 必ず再テストして `docs/` に記録するのがルールです。

## 5. `selector.py` — 本番の入口

複数ミッションをハブのボタンで選んで動かす、競技本番用のファイルです。

- **`dev` 設定**（`selector.py:43`）:
  - `True` … 走りながらセンサーの値も画面に表示（デバッグ向け）。
  - `False` … 表示なし（本番向け。通信が減って少し軽い）。
- **`programs` 一覧**（`selector.py:59`）: `{"module": モジュール, "display_number": 番号}`
  を並べたリスト。ここに並べた順がハブでの選択順になります。
- **操作**: 左右ボタンで番号を選び、フォースセンサー(C)を押すと実行。LED の色で状態が
  分かります（緑＝次へ・青＝前へ・赤＝実行中またはエラー）。
- **毎回リセット**: ミッションの前後で `reset_robot()` を呼び、向きや距離を 0 に戻します。
  前のミッションの状態が次に持ち越されないようにするためです。
- 1 つのミッションがエラーで落ちても、`try/except` で受け止めてセレクターは動き続けます。

> ここは競技の生命線です。`dev` の付け間違いや `programs` の並び順ミスは本番の事故に
> 直結します。編集は担当 1 人にまとめるのが安全です。

## 6. `run_*.py` の名前の付け方

```
run<ラン番号>_<ミッション>_<担当者>.py    例: run1_M01_M02_kanna.py
run_<ミッション>_<担当者>.py               例: run_M01_kidachi.py
run_<担当者>_<ミッション>.py               例: run_keiichiro_M12.py
run_test_*.py                              性能テスト用（競技では使わない）
```

- **同じミッションでも、担当者ごとにファイルを分けています。** お互いのコードを壊さずに
  自由に試せるようにするためです。他人のファイルは勝手に直さないのがマナーです。
- 新しく作るときは `run_template.py`（雛形）をコピーして、`run()` の中に動きを書きます。
  本番で使うときだけ `selector.py` の一覧に足します。
- `old/` フォルダは昔のファイル置き場です（参照だけ。ruff のチェック対象外）。

## 7. 開発を支える道具たち（PC 側）

### 7.1 ruff（整形＆チェック）

ruff の仕事は **「整形(format)」** と **「チェック(check / lint)」** の 2 つで、別物です。
設定は `pyproject.toml` にあります（対象 Python 3.9、1 行 100 文字 など）。

#### ① 整形（`ruff format`）— 見た目だけそろえる

**動作は一切変えず**、書き方の見た目を統一します。直すのは次のようなところ:

| 直すもの | 例 |
|----------|-----|
| 演算子・カンマ周りの空白 | `x=[1,2,3]` → `x = [1, 2, 3]` |
| インデント | スペース4つにそろえる |
| クォート | `'abc'` → `"abc"`（ダブルに統一） |
| 空行の数 | 関数と関数の間は2行あける |
| 行末の余分な空白 | 削除する |

```python
# 整形前
x=[1,2 ,3]
def  f( a ):
    return a

# 整形後
x = [1, 2, 3]


def f(a):
    return a
```

#### ② チェック（`ruff check`）— 問題を見つける

`pyproject.toml` の `select = ["E", "F", "I", "B", "UP"]` で、**5 種類**のルールを
有効にしています。それぞれ何を見ているか:

| 記号 | 名前 | 何を見る | 例 |
|------|------|----------|-----|
| **F** | Pyflakes | **バグの芽**。未使用 import / 未使用変数 / 未定義の名前の使用 / 二重定義 | `import os` したのに使っていない |
| **E** | pycodestyle | PEP8（公式スタイル）違反。空白・インデントの崩れ | 関数前の空行が足りない |
| **I** | isort | **import の並び順**（標準→外部→自作、アルファベット順） | import がバラバラ |
| **B** | bugbear | **ありがちな罠**。事故りやすい書き方を警告 | デフォルト引数に `[]`/`{}` を使う |
| **UP** | pyupgrade | **古い書き方を新しく**（3.9 で使える範囲で） | `"%s" % x` → f-string |

`ruff check --fix` を付けると、このうち自動で直せるもの（import 並べ替え・不要 import 削除
など）は自動修正されます。一番効くのは **`F`（Pyflakes）** で、「使い忘れ・定義し忘れ」など
**実行する前にバグを見つけて**くれます。

```python
import os          # F: os を使っていない（未使用 import）

def calc():
    result = 1 + 2 # F: result を使わずに捨てている（未使用変数）
    return value   # F: value がどこにも定義されていない

def add(items=[]): # B: デフォルト引数に [] は危険（呼び出し間で共有されて事故る）
    ...
```

#### ③ このプロジェクト独自のゆるめ設定

- **`ignore = ["E501"]`** … 「1 行が長すぎる」は指摘しない（100 文字を超えてもOK）。
- **`run*.py` / `run_template.py` は `F401` と `I001` を除外** … 「未使用 import」と
  「import 並べ替え」を**しない**。子どもが学習用にまとめて書いて残した import を、
  自動修正で消したり並べ替えたりして混乱させないため。
- **`old/` と `.venv` はチェックしない**（`extend-exclude`）。

### 7.2 ruff が走るタイミングは「2 つ」ある

ruff は別々の 2 か所から自動で走ります。役割が違うので両方知っておきましょう。

1. **F5 を押したとき**: `tasks.json` の `ruff: all` が「.py か確認 → format → check --fix」を
   順に実行します（`launch.json` のすべての構成で実行前に走る）。
2. **`git commit` したとき**: `.pre-commit-config.yaml` の設定で ruff が走ります
   （`pre-commit install` をした場合）。

### 7.3 変更履歴の自動記録（agy 連携）

`run_*.py`（アンダースコア始まりのものだけ。`run1_` のような数字始まりは対象外）を
コミットすると、変更の履歴を **自動で 3 か所に書いてくれる**仕組みがあります。

```
git commit
  └─ pre-commit フック（scripts/hooks/pre-commit）が、変更された run_*.py を見つける
       └─ scripts/changelog_hook.py が動く
            ├─ 変更内容(diff)を AI(agy)に渡して、日本語1行に要約してもらう
            │   （AI が使えないときは「+10/-3 行」のような機械的な文に切り替え）
            └─ 次の3か所に書き込んで、自動で git add する:
                 ① その run_*.py の先頭コメントの【更新履歴】に1行
                 ② docs/logs/<ファイル名>/HISTORY.md の表に1行
                 ③ docs/logs/<ファイル名>/YYYYMMDD_作業ログ.md に「要約＋差分」
```

- 要約には **agy（Antigravity という AI の CLI）** を画面なしモード（`-p`）で使います。
  Windows の agy は画面なしだと返事をしない仕様のため、Windows からは WSL 側の agy に
  橋渡しして使います（`changelog_hook.py:60-73`）。
- 担当者の名前はファイル名から推測します（例: `keiichiro` を含む → Keiichiro）。
- 記録に失敗してもコミットは止まりません（警告だけ出ます）。

> ⚠️ **注意**: git のフック（`.git/hooks/pre-commit`）は 1 つしか置けません。
> ruff 用の設定（`pre-commit install`）と、この変更記録用（`scripts/install-hooks.sh`）は、
> **同じ場所を上書きし合います**。両方を同時に効かせたい場合は、片方からもう片方を
> 呼び出すように 1 つにまとめる必要があります（今は別々）。
> ruff は F5 のときにも走るので、変更記録フックの方を入れておく運用と相性が良いです。

### 7.4 `run_with_log.py`（記録を残して実行）

`pybricksdev` でハブに送るのと同じことをしつつ、画面に出る内容を
`docs/logs/<ファイル名>/<日時>.log` にも保存する道具です。VS Code の「📝 Robot N + Log」
構成から呼ばれます。「さっきの失敗、なぜ？」と後から見返すときに便利です。

## 8. VS Code と実行環境

- **`launch.json`**: 「🤖 Robot 1〜5」（普通に実行）と「📝 Robot 1〜5 + Log」（記録付き）の
  **合計 10 個**の実行構成が入っています。どのハブに送るかは `--name "Pybricks HubN"` で
  決まります。すべて実行前に ruff が走り、文字化け防止の設定(`PYTHONUTF8=1`)も付いています。
- **`tasks.json`**: ruff を走らせるための設定。Windows と Mac/Linux でパスの書き方が違うので、
  `windows:` の部分でその差を吸収しています。
- **`.venv`（プロジェクト専用の道具箱・Git には入れない）**: ruff などの開発ツールと、
  pybricks などの実行用ライブラリの**両方**をここに入れます。
  注意点として、F5（デバッグ実行）は**「ターミナルで有効化した venv」ではなく
  「VS Code で選んでいる Python」**を使います。だから `.venv` を選んでおかないと
  `No module named pybricksdev` になります（前に直したのがこれ）。
- **BLE で動かせるのは Windows と Mac だけ**です。WSL からは BLE 接続できないので、
  実行は Windows 側の Python で行います。

### 8.1 `.venv` とは何か・なぜ必要か

`.venv` は **「このプロジェクト専用の Python 道具箱」**です。中に **Python 本体のコピー**と、
このプロジェクトで使うライブラリ（`pybricksdev`・`ruff` など）**だけ**が入った、独立した
フォルダです。

**なぜ必要？** もし `.venv` を使わないと、PC に 1 つだけある共通の Python に、すべての
プロジェクトのライブラリを混ぜて入れることになります。すると——

```
共通の Python（1つだけ）
├─ プロジェクトA … pybricks 4.0 が必要
├─ プロジェクトB … pybricks 2.0 が必要   ← どちらか片方しか入れられない！
└─ ほかのツールも全部ここに混ざる
```

…のように **バージョンの取り合い**が起き、1 つ消すと別のプロジェクトが動かなくなります
（俗に言う「依存関係の地獄」）。プロジェクトごとに箱を分ければ、これが全部なくなります。

`.venv` を使う利点:

1. **干渉しない** — 他プロジェクトとライブラリのバージョンがぶつからない。
2. **再現できる** — `requirements.txt` ＋ `.venv` で、新しい PC でも同じ環境を作れる
   （だから README に `pip install -r requirements.txt` の手順がある）。
3. **PC を汚さない** — システムの Python はきれいなまま。
4. **使い捨てできる** — 壊れたらフォルダごと消して作り直せる（だから `.venv` は Git に入れない）。

このプロジェクトの `.venv` に入っているもの:

| 入っているもの | 役割 |
|----------------|------|
| Python 本体のコピー | この箱専用の Python |
| `pybricksdev` | コードをハブに送るツール |
| `ruff` / `pre-commit` | 整形・チェック |
| `pybricks` | エディタの補完・チェック用（実体はハブ側で動く） |

> 💡 最初に起きた `ruff' is not recognized`（箱がまだ無かった）や
> `No module named pybricksdev`（VS Code が `.venv` ではなく別の Python を見ていた）は、
> どちらもこの「道具箱」まわりのトラブルでした。
> 「`.venv` を作る → ライブラリを入れる → VS Code にこの箱を使わせる」で解決します。

### 8.2 `.venv` の中身は OS によって違う

同じ `python -m venv .venv` を実行しても、**できあがる中身は Windows と Mac/Linux で
別物**です（Python の仕組み上そうなっています）。`tasks.json` が `.venv\Scripts`(Win) と
`.venv/bin`(Mac/Linux) を使い分けているのも、`README.md` の準備コマンドが
`.venv\Scripts\activate` と `source .venv/bin/activate` に分かれているのも、この違いが理由です。

```
Windows (.venv\)                         macOS / Linux (.venv/)
├── Scripts\        ← 実行ファイル置き場    ├── bin/         ← 実行ファイル置き場
│   ├── python.exe                        │   ├── python
│   ├── pip.exe                           │   ├── pip
│   ├── ruff.exe                          │   ├── ruff
│   ├── activate.bat    (cmd 用)          │   ├── activate       (bash/zsh 用)
│   └── Activate.ps1    (PowerShell 用)   │   ├── activate.csh
│                                         │   └── activate.fish
├── Lib\                                  ├── lib/
│   └── site-packages\  ← ライブラリ本体    │   └── pythonX.Y/site-packages/ ← ライブラリ本体
└── pyvenv.cfg                            └── pyvenv.cfg
```

違いをまとめると:

| 項目 | Windows | macOS / Linux |
|------|---------|---------------|
| 実行ファイルのフォルダ | `Scripts\` | `bin/` |
| 実行ファイル名 | `python.exe`・`ruff.exe`（`.exe` が付く） | `python`・`ruff`（拡張子なし） |
| ライブラリの場所 | `Lib\site-packages\` | `lib/pythonX.Y/site-packages/` |
| 有効化スクリプト | `activate.bat` / `Activate.ps1` | `activate` / `activate.csh` / `activate.fish` |

> ⚠️ **1 つの `.venv` フォルダを Windows と Mac で共用することはできません。**
> 実行ファイルが OS ごとの別物であるうえ、`.venv` 内の設定ファイル(`pyvenv.cfg`)が
> 「この PC のこの Python を使う」という**具体的な場所（絶対パス）**を覚えているからです。
> だから `.venv` は Git に入れず（gitignore 済み）、**PC ごと・OS ごとに自分で作り直す**
> 前提になっています。1 台で Windows と WSL を併用する場合も、それぞれ別の `.venv` が必要です。

### 8.3 実行するハブはどう選ばれるか

短く言うと、**「VS Code でどの実行構成を選ぶか」**でハブが決まります。ハブに番号を
送っているのではなく、**Bluetooth の「名前」で目的のハブを指名**しています。

```
あなたが「実行とデバッグ」のドロップダウンで構成を選ぶ
    例: 「🤖 Robot 3 (Pybricks Hub3)」
          │  F5
          ▼
launch.json のその構成が pybricksdev にこう渡す:
    pybricksdev run ble <開いているファイル> --name "Pybricks Hub3"
          │                                        └─ ここがハブの指名
          ▼  BLE（無線）でスキャン
"Pybricks Hub3" という名前で電波を出しているハブを探して接続し、コードを送る
```

- 決め手は **`--name "Pybricks HubN"`**。これが「どのハブに送るか」を指定します。
- ハブの名前は **Pybricks ファームウェアを書き込むとき**（code.pybricks.com）に付け、
  `Pybricks Hub` / `Pybricks Hub2` / … / `Pybricks Hub5` の5つに統一する決まりです。
- `launch.json` には 5 台 × (通常・ログ付き) = **10 構成**が用意済み。「Robot 3」を選べば
  自動的に `--name "Pybricks Hub3"` が渡ります（「+ Log」構成も `run_with_log.py:41` 経由で
  同じ `--name` を渡すだけ）。

| VS Code で選ぶ構成 | 渡る名前 | つながるハブ |
|--------------------|----------|--------------|
| 🤖 Robot 1 | `Pybricks Hub` | 1台目 |
| 🤖 Robot 2 | `Pybricks Hub2` | 2台目 |
| … | … | … |
| 📝 Robot 3 + Log | `Pybricks Hub3` | 3台目（記録付き） |

**「ハブの選択」と「ミッションの選択」は別もの**なので混同しないこと:

| 何を選ぶ？ | どこで選ぶ？ | しくみ |
|------------|--------------|--------|
| どのハブに送るか | PC の VS Code 構成（`--name`） | pybricksdev が BLE 名で接続 |
| どのミッションを動かすか | ハブの左右ボタン＋フォースセンサー | `selector.py` の `programs` から選ぶ（§5） |

> つまり「PC 側でハブを指名 → ハブ側でミッションを選ぶ」の2段階。
> よくあるつまずき: **構成を選び間違えると別のハブにつながる**／**`--name` と
> ハブ名が1文字でも違うと「No matching device found」**／**ハブの Bluetooth ボタンを
> 押して青く点滅させていないと見つからない**。

### 8.4 `.vscode/` の設定は OS に依存する？

`.vscode/` の 3 つのファイルは、それぞれ事情が違います。

| ファイル | OS 依存？ | どう対応しているか |
|----------|-----------|--------------------|
| **launch.json** | ❌ 依存しない | OS 固有のパスを書かず、`module: pybricksdev` や `${file}` などの**変数**で書いている |
| **tasks.json** | ⚠️ 依存する（対応済み） | `windows:` キーで Windows と Mac を**分岐**している |
| **settings.json** | ✅ 依存しない（対応済み） | OS 依存のパスを直書きせず、`.venv` の**自動検出**に任せる |

**launch.json** … ハブへ送るコマンドを `module` 名と `${file}` で書いているので、
OS ごとに VS Code が解決します。直書きの Windows パスが無いため、そのまま両 OS で動きます。

**tasks.json** … 本来 OS 依存（`.venv\Scripts` 対 `.venv/bin`、`powershell` 対 `/bin/zsh`）
ですが、`windows:` セクションで切り替えて両対応にしています。

```jsonc
"env": { "PATH": "${workspaceFolder}/.venv/bin:..." },              // Mac
"windows": { "env": { "PATH": "${workspaceFolder}\\.venv\\Scripts;..." } } // Windows
```

**settings.json** … ⚠️ ここは注意が必要でした。当初インタプリタを
`${workspaceFolder}/.venv/Scripts/python.exe` で固定していましたが、これは **Windows 専用**で
（Mac は `.venv/bin/python`）、Mac では効きません。しかも settings.json には tasks.json の
`windows:` のような**OS 分岐キーが無い**ため、1 つのパスで両対応にはできません。

そこで **インタプリタのパス固定をやめ**、Python 拡張機能による `.venv` の自動検出に任せる形に
しました（`python.terminal.activateEnvironment` だけ残す）。各自、初回だけ
「Python: Select Interpreter」で `.venv` を選べば VS Code が記憶します。

> まとめ: **launch.json は元から OS 非依存**、**tasks.json は分岐して両対応**、
> **settings.json は OS 依存パスを外して両対応にした**。
> 「OS で形が変わるのは `.venv` の中身（§8.2）」という1点さえ押さえれば、設定ファイルの
> 作り分けの理由はすべて説明できます。

## 10. まとめ — 守ること・増やすとき・弱いところ

**守ること（崩すと動かない）**
- ポート: F=左タイヤ / B=右タイヤ / E=左アーム / A=右アーム / C=フォースセンサー。
- ハブの向き（上=Z・前=X）、タイヤ径 62mm、左右間隔 85mm。
- ミッションは決まった形の `async def run(hub, robot, left_wheel, right_wheel, left_lift, right_lift)`。
- BLE 実行は Windows / Mac のネイティブ Python で（WSL では不可）。

**増やすとき**
- 新しいミッション → `run_template.py` をコピー → `run()` を書く →（本番で使うなら）`selector.py` に登録。
- 6 台目以降のハブ → `launch.json` に実行構成を 2 つ追加（手順は `README_FOR_MENTORS.md` §4.5）。
- 機体を作り替えた → `setup.py` の数値（タイヤ径・PID など）を更新して、走行テストをやり直す。

**弱いところ（知っておくと良い）**
- git のフックを ruff 用と変更記録用が取り合う（§7.3）。
- 変更履歴の自動記録は `run_*.py`（アンダースコア始まり）だけが対象。`run1_` などは対象外。
- `docs/logs/` は今は Git に入る。増えすぎたら gitignore や別管理を検討。
- `setup.py` 1 つに全機体が相乗りなので、機体ごとの差（タイヤ径違いなど）には本来弱い。
