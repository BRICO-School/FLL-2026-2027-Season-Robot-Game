# 試行記録（トライアルログ）仕様案

> 目的: 「いつ・どのミッションを・何回走らせて・何回成功したか」を残し、
> プレゼンで **時系列の試行回数と成功率の改善** を語れるようにする。
>
> 大前提: **ハブ側のコード（`setup.py` / `selector.py` / `run_*.py`）は一切変更しない。**
> 記録はすべて PC 側、ロボット制御の外側で行う。

---

## 1. 設計方針

| 方針 | 理由 |
|------|------|
| ハブ側コードは触らない | ロボットの動作・タイミング・メモリに影響を与えない。記録の不具合で走行が止まるリスクをゼロにする |
| 既存の `run_with_log.py` の**後段**に足す | すでに「PC 側で pybricksdev を包む」場所がここにある。走行が終わった**あと**に成否を聞くだけなので走行中は何もしない |
| 成否の判定は**人が入力** | ハブは「ミッションが成功したか」を知らない（点数はフィールド上の物理結果）。走行直後に子どもがキー 1 つで答えるのが最も確実で、教育的にも「自分で判定して記録する」経験になる |
| 記録は CSV 1 ファイル、追記のみ | Excel / Google スプレッドシートで開ける。git 管理して複数 PC で共有 |
| 集計・グラフは別スクリプト | 記録と可視化を分ける。プレゼン直前に 1 コマンドで最新の表と図を出す |

---

## 2. 全体の流れ

```
F5「📝 Robot N + Log」
  └─ run_with_log.py
       ├─ pybricksdev でハブへ送信・実行（ここは今まで通り、無変更）
       ├─ 実行ログを docs/logs/<script>/<timestamp>.log に保存（今まで通り）
       └─ ★ 走行終了後、ターミナルで成否を 1 キーで聞く   ← 新規
              o=成功  x=失敗  d=途中まで  s=記録しない
            └─ docs/trials/trials.csv に 1 行追記

scripts/trial_report.py（プレゼン前に手で実行）
  └─ trials.csv を集計 → docs/trials/report.md ＋ グラフ PNG
```

ロボットへの送信・実行部分には手を入れない。追加されるのは「実行が終わって
プロセスが返ってきた後」の入力と、ファイル追記だけ。

## 3. 記録するデータ

保存先: `docs/trials/trials.csv`（UTF-8、ヘッダ付き、追記のみ）

| 列 | 例 | 説明 | 入力元 |
|----|----|------|--------|
| `trial_id` | `20260909_183012` | ログファイル名と同じタイムスタンプ。ログと 1:1 で対応 | 自動 |
| `date` | `2026-09-09` | 集計用の日付 | 自動 |
| `time` | `18:30:12` | | 自動 |
| `script` | `run_M01_kidachi.py` | 実行したファイル | 自動 |
| `mission` | `M01` | ファイル名から M 番号を、書いてある順に抽出（`M9` は `M09`）。複数なら `M05+M06+M07`（§9） | 自動（推定） |
| `member` | `kidachi` | ファイル名から推定（`run_M01_kidachi` → `kidachi`）。取れなければ空 | 自動（推定） |
| `hub` | `Pybricks Hub4` | `--name` 引数 | 自動 |
| `result` | `success` / `fail` / `partial` | 成否。ミッションが複数なら `mission_results` から自動で決める（§9） | **人が入力** |
| `elapsed_sec` | `19.2` | pybricksdev 起動から終了まで（ハブを探す・接続・送る・ジャイロの待ちを含む。集計には使わない） | 自動 |
| `exit_code` | `0` | 0 以外なら BLE 未接続やハブ側エラー | 自動 |
| `commit` | `23f1723` | 実行時の `git rev-parse --short HEAD`。「このコード変更で成功率が上がった」を語る根拠 | 自動 |
| `note` | `右アームが早すぎた` | 任意メモ（Enter で空欄） | 人が入力（任意） |
| `log_path` | `docs/logs/run_M01_kidachi/20260909_183012.log` | 詳細ログへのリンク | 自動 |
| `code_hash` | `a3f9c1e2` | 走行した `run_*.py` ＋ `setup.py` の内容ハッシュ（短縮）。同じ値なら同じコードで走った | 自動 |
| `snapshot` | `docs/trials/snapshots/a3f9c1e2/` | 走行時のコードのコピー先（§4.5） | 自動 |
| `via` | `selector P3` | selector 経由ならハブ画面の番号。直接実行なら空（§4.4） | 自動 |
| `mission_results` | `M12=fail M11=success M07=unreached` | ミッションごとの成否（2026-10-03 追加・§9）。空の古い行は `result` を全ミッションに当てる | **人が入力** |
| `run_sec` | `5.1` | 本番でもかかる時間（2026-10-03 追加・§10）。「初期化完了 → 走行完了」、セレクターは「実行中 → 実行完了」。測れなければ空 | 自動 |

`result` の値:

| 入力キー | 値 | 意味 |
|---------|-----|------|
| `o` | `success` | ミッション達成 |
| `x` | `fail` | 達成できず |
| `d` | `partial` | 途中まで・一部達成（成功率の分母には入れる、分子には入れない） |
| `s` | （記録しない） | 走らせ間違い・ケーブル抜けなど「試行」と呼べないもの |
| `e` | `error` | ロボットが動く前に止まった（`exit_code != 0` のときの既定値） |
| `-` | `unreached`（`mission_results` の中だけ） | 届かなかった。前のミッションのせいで挑戦できなかった。そのミッションの分母に入れない（§9） |
| `b` | — | 1 つ前の質問に戻る（§9） |

## 4. `run_with_log.py` への追加仕様

### 4.1 変更しない部分

- pybricksdev の起動コマンド、引数、ログ保存の挙動は現状維持。
- 走行中の標準出力の中継も現状維持。走行中に stdin を読んだり待ったりしない。

### 4.2 追加する部分（プロセス終了後のみ）

> 2026-10-03 から、聞き方は §9 の形（ミッションごとに 1 つずつ・`b` で戻る・最後に確認）になった。下は最初の版の記録。

1. `process.wait()` が返ったあと、ターミナルに次を表示して 1 キー待ち:
   ```
   ──────────────────────────────
   🏁 結果を記録します: run_M01_kidachi.py (M01)
      o=成功  x=失敗  d=途中まで  e=動かなかった  s=記録しない
   結果 >
   ```
2. 続けて `メモ（なければ Enter）>` を表示。
3. `docs/trials/trials.csv` に 1 行追記（ファイルが無ければヘッダ付きで作成）。
4. 追記後に `📊 記録しました: M01 success（今日 M01: 3/5 成功）` と、その日その
   ミッションの成功数/試行数を表示する。子どもがその場で数字を見られると励みになる。

### 4.3 例外・特殊ケース

- **記録処理で例外が起きてもプロセスの終了コードは pybricksdev のものを返す。**
  記録失敗は警告表示のみ（changelog フックと同じ思想）。
- `--no-trial` オプション、または環境変数 `TRIAL_LOG=0` で成否入力を丸ごとスキップ
  （`verification/run_lift_motor_test.py` のような機構テストや、繰り返しループ用）。
- `exit_code != 0`（BLE が見つからない等）のときは既定値を `e` にして、Enter だけで
  記録できるようにする。
- 入力待ちに **タイムアウトは設けない**。ただし Ctrl+C で抜けたら「記録しない」扱い。
- VS Code の debugpy から起動した場合も、`console` が `integratedTerminal`（既定）なら
  `input()` は動く。`internalConsole` にはしない。

### 4.4 `selector.py` 経由の通し練習

`selector.py` は 1 プロセスで複数ミッションを走らせるため、1 プロセス＝1 試行の
前提が崩れる。**ハブ側は変えない**ので、PC 側で標準出力を**読むだけ**で対応する:

- `selector.py` は既に `=== プログラム N を実行中 ===` / `=== プログラム N 実行完了 ===`
  を print している。`run_with_log.py` が中継中にこの行を**見つけたら**（何もブロック
  せず）番号と時刻を控えておく。
- プロセス終了後、控えた回数分だけ「プログラム 1 の結果 >」「プログラム 2 の結果 >」
  と順に聞く。`mission` 列にはプログラム番号（`P1` など）と、`selector.py` の
  `programs` 順から引いたモジュール名を入れる。
- 標準出力の読み取りは既存のループに `if line.startswith("=== プログラム")` を
  足すだけで、ハブとの通信には影響しない。
- 2026-10-03 から: プログラムごとに §9 の形でミッションの順に聞き、全部聞きおえて確認で Enter を押したときに
  まとめて書く。`b` で 1 つ前のプログラムにも戻れる。
- 実装: `SelectorWatcher` が「実行中」「実行完了」「エラー:」「セレクターに戻りました」の
  行を控え、終了後に `record_selector_trials()` が 1 回ずつ聞く。`script` 列には走った
  モジュール名（`run1_M10_M11.py` など）、`via` 列にハブ画面の番号が入る。
  スナップショットはそのモジュール＋`setup.py` なので、単体実行と同じコードなら
  同じ `code_hash` になり、集計が混ざらない。エラー行があった回は既定キーが `x`。

### 4.5 走行時のコードをそのまま保存する（スナップショット）

「その試行はどのコードで走ったか」を後から正確に見られるように、成否を記録する
タイミングで**実行したファイルをコピーして残す**。ハブへ送ったあとの PC 側の
ファイルコピーなので、走行には影響しない。

- 保存するもの:
  - 実行した `run_*.py`
  - `setup.py`（速度・PID・ポート設定はここにあり、走行結果を左右する）
  - `selector.py` 経由のときは `selector.py` と `programs` に登録された全モジュール
- 保存先: `docs/trials/snapshots/<code_hash>/` に元のファイル名のまま置く。
- `code_hash` は保存対象ファイルの内容を連結した SHA-256 の先頭 8 桁。
  **同じハッシュのフォルダが既にあればコピーしない**（同じコードで 10 回走らせても
  コピーは 1 つ）。CSV には毎回 `code_hash` を書くので、試行と対応付けできる。
- 容量の目安: 1 スナップショット 10KB 前後。コードを変えるたびに 1 つ増えるだけなので
  シーズン通しても数 MB に収まる。git 管理してよい。
- なぜコミットハッシュだけでは足りないか: 練習中はコミット前の編集で走らせることが
  ほとんどで、`commit` 列だけでは走ったコードを復元できない。スナップショットは
  その穴を埋める。逆に `commit` 列は「どの変更のあとか」を大まかに追う用途に残す。
- レポートでの使い方: `code_hash` が変わった点をグラフに縦線で入れると
  「ここでコードを直したら成功率が上がった」が一目で示せる（§5）。

## 5a. ダッシュボード `scripts/trial_dashboard.py`（2026-09-19 追加）

`docs/trials/trials.csv` から、ブラウザで開ける 1 枚の HTML（`docs/trials/dashboard.html`）を作る。
外部ライブラリなし・ネット接続なし。`run_with_log.py` が成否を記録するたびに自動で作り直すので、
ふだんはブラウザで開いたまま再読みこみ（F5）するだけでよい。手で作るときは:

```
uv run python scripts/trial_dashboard.py --open
```

開発の進め方「① run ファイルで要素開発 → ② セレクターから通し」に合わせた構成（2026-09-19 見直し）:

作り（2026-09-19・make-html スキルの作法を反映）: 答える問いは「いま何点取れそうで、次にどのミッションに手を入れるか」の 1 つ。
数字はぜんぶ Python で計算し、出てくる HTML には**スクリプトが無い**（しぼりこみは無くした。Obsidian の HTML ビューアーの Safe モードでも読める）。
見た目は weekly 型の見本（html-effectiveness の `ja/11-status-report.html`）で、CSS は `scripts/dashboard_style.css` に見本のまま写してある
（足した部品は `trial_dashboard.py` の `EXTRA_CSS` だけ）。節は 数字 4 つ → ハイライト → 点数マップ → ① 要素開発 → ② 通し → 日ごとの試行 → メンバーごと → 最近の試行 → 次に手を入れるところ。
記録の無い節は出さない。「動かなかった」も数えるときは `--include-error`。

**チームとコーチを分ける**（2026-10-02）: run ファイルの名前に `coach` が入る記録（`run_coach_M01.py` など。セレクター経由もふくむ）は
コーチが確かめるために走らせたものなので、`dashboard.html` には**数えない**。そのぶんだけを集めた `docs/trials/dashboard_coach.html` を
同じ作りで別に作る（「メンバーごと」の節は出さない）。2 枚の見出しの下に、おたがいへのリンクがある。どちらも記録のたびに作り直される。

- **いまの見こみ点** ＝ Σ（ミッションの満点 × 直近 3 回の成功率）。満点の表は `scripts/bioglow_missions.py`
  （公式の採点表とルールブックから。ミッション 460 点＋装備の点検 20 点＋精密トークン 最大 50 点＝ 530 点）。
  直近 3 回は `EXPECTED_N`（オーナー 2026-10-05 に直近 10 本 → 3 回に変更）
- **点数マップ**: 15 ミッションの満点・段階・試行・直近 3 回の成功率・見こみ点・平均秒・担当・直近の成否の並び。
  秒はすべて `run_sec`（本番でもかかる時間・§10）。`run_sec` の無い古い記録は時間の集計に入れない。
  最後に「ミッションの小計」「装備の点検（参考）20」「精密トークン（参考）50」「合計（参考値をふくむ）」の行を出す（2026-10-03）。
  点検と精密トークンは **取れる前提の参考値**（`scripts/bioglow_missions.py` の `EXTRA_POINTS`。ルールブック p.8・Rule 15）。
  グレイシャス・プロフェッショナリズム（2〜4 点）はロボットゲームの得点ではなく審査のコアバリューに足される（p.17）ので入れない。
  数字の帯の「いまの見こみ点」は参考値こみの合計（○ / 530）で、「ミッション ○ ＋ 点検・精密トークン 70（参考）・時間の合計 ○ 秒 / 150 秒」を添える。
  ミッションの平均秒は、時間を測れた本（成否に関わらず）の `run_sec` の平均。**続けて回る run**（`run_coach_M12M11M06M07.py` など）は、
  1 本の時間をファイル名の最初のミッション（M12）に出し、ほかのミッションは「-」（全体の時間が分かり、合計で重ねて数えない・オーナー 2026-10-03）。
  時間の合計にホームでの付けかえは入らないので、本当の通しの時間は ② 通しで見る。150 秒をこえたら「オーバー」と出る。
  段階は 未着手／要素開発中（単体の記録だけ）／単体で安定（直近 10 本・5 本以上で 80% 以上）／通しに入れた（`via` が selector の記録あり）／通しで安定
- **① 要素開発**: `via` が空の行を run ファイルごとに。直近 10 本・通算・平均秒・コードの版（`code_hash` の種類）・直近の並び
- **② 通し**: `via` が `selector P<n>` の行を「通し 1 回」にまとめる（同じログの中で、同じプログラムがもう一度出たとき・90 秒あいたときに次の回）。
  1 回ごとの見こみ点（成功したプログラムのミッションの満点の合計）と、最初のスタートから最後のゴールまでの時間（試合は 150 秒）
- 日ごとの試行数と成功率（直近 14 日）／メンバーごと／最近の 20 本／次に手を入れるところ（のびしろの大きい順・単体で安定したもの・時間オーバー・満点の高い未着手）

**ミッション単位で数える**（2026-10-03・§9）: 成功率・見こみ点・段階はミッションごとの成否で数え、「届かなかった」は分母に入れない。
「試行」は走らせた本数のまま。① 要素開発の「ミッション」の列は、複数ミッションの run ではミッションごとの 成功/挑戦（`M12 0/11 · M11 1/2`）。
最近の試行と ② 通しは、ミッションごとの結果を色の点で並べる。

限界: 見こみ点は「成功＝満点・それ以外＝ 0 点」の目安。「届かなかった」を入れないので「届けば取れる点」で、通しの本当の点は ② 通しの回ごとの点で見る。
ボーナスだけ・一部だけ取れた点、精密トークン（ホームの外で手を出した回数）は記録していない。
ミッション番号はファイル名から読む（`run_M04_kanna.py` → M04、`run_M07M09_x.py` → M07+M09）ので、**run ファイルの名前に M 番号を走る順に入れること**。
成功率の分母は そのミッションの 成功＋途中まで＋失敗（「届かなかった」は入れない。「動かなかった」は `--include-error` のときだけ数える）。
`dashboard.html` は生成物なので **git には入れない**（`.gitignore`）。コーチ用の `dashboard_coach.html` は、生成物だが共有のため **git に入れる**（2026-10-03）。プレゼン用の表と PNG は下の `trial_report.py`。

## 5. 集計・可視化 `scripts/trial_report.py`

```
python scripts/trial_report.py            # 全期間
python scripts/trial_report.py --since 2026-09-01
python scripts/trial_report.py --mission M01
```

出力:

1. `docs/trials/report.md`
   - ミッション別 × 週別の「試行数 / 成功数 / 成功率」表
   - メンバー別の試行数
   - 直近 10 試行の一覧
2. `docs/trials/charts/success_rate_<mission>.png`
   - 横軸: 日付（週）、縦軸: 成功率（折れ線）＋ 試行数（棒）
   - プレゼン用の「見せる図」。matplotlib を `requirements-dev.txt` に追加
     （ハブ側には無関係な PC 専用依存）
3. `docs/trials/charts/all_missions.png`: 全ミッション合算の試行回数累計と成功率
4. ミッション別グラフには `code_hash` が切り替わった位置に縦の点線を入れ、
   「コード変更 → 成功率の変化」を対応付けて見せる。`--diff` オプションで
   隣り合うスナップショット同士の差分（`difflib`）を `report.md` に添える

`partial` は「試行したが成功ではない」として分母にのみ入れる。`error` は
ロボットが動いていないので既定では**分母から除外**し、`--include-error` で含める。
2026-10-03 から、ミッションが複数の走行はミッションごとに分けて集計する（`M05+M06` をひとかたまりにしない）。
`unreached`（届かなかった）は分母に入れない。`--mission M9` のような指定は `M09` にそろえる。

## 6. git 運用

- `docs/trials/trials.csv`、`snapshots/`、`report.md`、`charts/*.png` は**すべて git 管理**する
  （`docs/logs/` と同じ扱い。ログは既に追跡されている）。
- 複数 PC が同じ日に追記して衝突しないよう、`.gitattributes` に
  ```
  docs/trials/trials.csv merge=union
  ```
  を追加する。追記専用ファイルなので、両側の行を残す union マージで安全に自動解決できる。
- `trial_id` はタイムスタンプ＋ハブ名で実質ユニーク。同秒に 2 台が走っても列が違うので区別できる。
- 個人情報の観点: `member` はファイル名にすでに含まれる呼び名のみ。それ以上は記録しない。

## 8. 検討して却下した案

| 案 | 却下理由 |
|----|---------|
| ハブ側 `run()` の末尾で成否をボタン入力させ print する | ハブ側コードの変更が必要。走行シーケンスに入力待ちが入り、大会本番用コードと練習用コードが分岐する |
| ログファイル (`docs/logs`) の有無だけで試行回数を数える | 回数は取れるが成否が分からない。成功率が語れない |
| Google スプレッドシートへ直接送信 | ネットワーク依存とトークン管理が増える。CSV を git で共有すれば十分で、必要ならあとで CSV を取り込める |
| 通常の 🤖 構成（ログなし F5）にも記録を付ける | pybricksdev を直接呼ぶ構成なので PC 側に挟む場所がない。「記録したいときは 📝 構成」と使い分けるほうが分かりやすい |

## 9. ミッションごとの成否（2026-10-03）

1 本の run で複数のミッションを回るとき（`run_coach_M12M11M06M07.py` など）、これまでは成否が 1 つしか記録できず、
ダッシュボードでは全部のミッションに同じ結果が付いていた。メモに「M12 x, M11 o」と書いても数えられなかった。
そこで、ミッションごとに成否を聞いて記録する。決めたこと（オーナー 2026-10-03）:

| 項目 | 決めたこと |
|------|-----------|
| ミッションと順番 | **run ファイルの名前に書いた順**。`run_M01M02M03_kanna.py` → M01 → M02 → M03。1 ミッションなら `run_M01_kanna.py`。`_` で区切ってもよい。`M9` は `M09` にそろえる。M01〜M15 にない番号と 2 回目の番号は数えず、記録の前に注意を出す |
| コーチのファイル名 | `run_coach_<M 番号を続けて>.py`（`run_coach_M12M11M06M07.py`）。同じミッションでもう 1 本あるときは後ろに短い言葉を足す（`run_coach_M03_teach.py`） |
| 聞き方 | ミッションごとに 1 つずつ「M12 の結果 [o] >」と聞く。1 ミッションの run は 1 回だけ |
| 届かなかった `-` | 前のミッションのせいで、そのミッションに挑戦できなかった。**そのミッションの分母に入れない**（成功率は「届いたときにできたか」＝そのミッションのプログラムの出来を表す） |
| 成功率 | **ミッション単位**。分母は そのミッションの 成功＋途中まで＋失敗。「試行」は走らせた本数のまま |
| 入力のやり直し | どの質問でも `b` で 1 つ前に戻れる（前のプログラムにも）。最後に確認の画面が出て、**Enter を押すまで何も書かない**。番号を押すとその本だけ入れ直せる |
| 記録したあとで直す | `uv run python scripts/trial_fix.py`。直近の記録を番号で選んで入れ直す。`s` でその記録を消す。この道具を通したときだけ、その 1 行の書きかえを許す（追記だけの例外） |
| 10/3 の記録 | メモにミッション別の結果がある 2 本（11:42・12:00）だけ書き足した。ほかは M12 だけの記録のまま |

### 9.1 聞き方の例

```
🏁 結果を記録します
run_coach_M12M11M06M07.py（M12 → M11 → M06 → M07）
   o=成功  x=失敗  d=途中まで  -=届かなかった ／ e=動かなかった  s=記録しない ／ b=1 つ前に戻る
M12 の結果 [o] > x
M11 の結果 [o] > o
M06 の結果 [o] > x      ← まちがえた
M07 の結果 [o] > b      ← 1 つ前に戻る
M06 の結果 [x] > o
M07 の結果 [o] > -
メモ（なければ Enter・b=戻る）> M11 のアームが早い

── この内容で記録します ──
 1  run_coach_M12M11M06M07.py（M12 → M11 → M06 → M07）  M12 失敗 / M11 成功 / M06 成功 / M07 届かなかった ／ メモ: M11 のアームが早い
Enter=記録する  番号=その本を入れ直す  b=1 つ前に戻る  s=記録しない >
📊 記録しました: M12 失敗 / M11 成功 / M06 成功 / M07 届かなかった（今日の成功: M12 0/12・M11 2/3・M06 3/3）
```

- `e`（動かなかった）と `s`（記録しない）は、その 1 本ぜんぶに効く。
- 走ったあとの既定値（Enter で入る値）は、成功 `o`。`exit_code` が 0 でないときは最初の質問だけ `e`、セレクターでエラー行があったプログラムは `x`。
- セレクターの通し練習では、プログラムごとに同じ形で聞き、最後の確認で全部まとめて書く。

### 9.2 記録の形

`trials.csv` の右端に `mission_results` 列を足した（見出しの行は、最初に記録したときに自動で書きかわる。古い行は空のまま読める）。

```
script,mission,...,result,...,via,mission_results
run_coach_M12M11M06M07.py,M12+M11+M06+M07,...,partial,...,,M12=fail M11=success M06=success M07=unreached
```

- `mission_results` は空白で区切った「ミッション=結果」。結果は `success` / `partial` / `fail` / `unreached`。
- `result` はミッションごとの結果から自動で決める: 届いたミッションが全部成功 → `success`、成功か途中までが 1 つでもある → `partial`、それ以外 → `fail`。
  1 本ぶんの結果を見る古い集計（今日の本数など）は、これまでどおり `result` を読める。
- `mission_results` が空の古い行は、`result` を `mission` 列のミッション全部に当てる（いままでと同じ数え方）。

### 9.3 部品

| ファイル | 役目 |
|---------|------|
| `scripts/trial_results.py` | 共通の部品。名前からミッションを読む・`mission_results` の読み書き・`result` を決める・ターミナルで聞く（`b`・確認）・見出しに列を足す・1 行だけ書きかえる |
| `run_with_log.py` | 走行のあとに聞いて追記する（単体・セレクター） |
| `scripts/trial_dashboard.py` | ミッション単位で数える（点数マップ・① 要素開発・② 通し・日ごと・メンバー・最近の試行） |
| `scripts/trial_report.py` | ミッションごとに分けて集計とグラフを作る |
| `scripts/trial_fix.py` | 記録したあとで直す・消す |

### 9.4 却下した案

| 案 | 却下理由 |
|----|---------|
| 1 ミッション = 1 行にする | 1 行 = 1 走行（ログ・スナップショットと 1 対 1）が崩れ、試行の本数が水増しされる。集計を全部書き直すことになる |
| ミッションの結果を別の CSV に分ける | 2 つのファイルの突き合わせが要り、複数 PC のマージでずれるおそれがある |
| ファイル名に M 番号を並べるだけ | 成否は 1 つのままなので、M12 の失敗が全部の失敗になる |
| run ファイルの中のコメントでミッションを宣言する | ファイル名と二重になる。ファイル名だけで決まるほうが子どもに分かりやすい（オーナー 2026-10-03） |
| 1 行で `xoo-` とまとめて打つ | 速いが、どの文字がどのミッションか分かりにくい。1 つずつ聞く（オーナー 2026-10-03） |
| 届かなかったミッションを失敗に数える | 前のミッションの失敗が、後ろのミッションの成功率まで下げる。直すべきところが分からなくなる |
| 点数そのもの（ボーナス・一部の得点）を入れる | 入力の手間が大きい。必要になったら次の段階で考える |

## 10. 本番でもかかる時間 `run_sec`（2026-10-03）

ロボットゲームは 150 秒。ダッシュボードで集計する時間は、**本番でもかかる時間だけ**にする（オーナー 2026-10-03）。

### 10.1 それまでの問題

| 問題 | 中身 |
|------|------|
| 単体の時間に本番に無い時間が入る | `elapsed_sec` は pybricksdev の起動から終了まで。ハブを探す・接続・送る（約 2.5 秒）・ジャイロの待ち（2.0 秒）・切断が入り、10/3 の M04 は 19 秒前後のうち走行は一部だけ。ログの行に時刻が無いので、あとから分けられない |
| ハブの行がまとめて遅れて届く | pybricksdev はハブの行を `print()` するだけで flush しない（`pybricksdev/connections/pybricks.py`）。パイプで受けると行がまとまって届く（1 秒おきの 4 行が 4 秒後に 4 行まとめて届いた。`-u` なら 0・1・2・3 秒）。セレクターの「実行中 → 実行完了」も正しく測れていなかった（セレクターの記録はまだ無かった） |

### 10.2 測り方（PC 側だけ・ハブのコードは変えない）

1. `run_with_log.py` は pybricksdev を `-u` と `PYTHONUNBUFFERED=1` で起動する（`verification/compare.py` と同じ）。
2. ハブがもう出している 2 行が PC に届いた時刻の差を `run_sec` にする（`time.monotonic()`）。
   - 始まり: `=== ロボット初期化完了 ===`（`setup.py` の `initialize_robot()` の最後）
   - 終わり: `# 走行完了！`（run ファイルの `run()` の最後。`run_template.py` の形の run ファイルにはある）
   - この間は `run()` の中だけで、セレクターから走らせたときと同じ中身。
3. セレクター経由は、プログラムごとの `=== プログラム N を実行中 ===` → `=== プログラム N 実行完了 ===` を `run_sec` にする（`reset_robot()` と 0.05 秒の待ちをふくむ。本番でも同じ）。
4. ログの最後と画面に「接続〜初期化完了 ○ 秒」「走行 ○ 秒」を出す（行の頭に時刻は付けない。`gyro_trace_summary.py` が行の頭の `T,` で読むため）。

測れないとき（途中で止めた・`# 走行完了！` の行が無い run ファイル）は `run_sec` を空にする。

### 10.3 集計

| 場所 | 使う時間 |
|------|---------|
| 点数マップの「平均秒」 | 時間を測れた本の `run_sec` の平均。続けて回る run は最初のミッションに 1 本の時間、ほかは「-」 |
| ① 要素開発の「平均秒」 | 成功した本の `run_sec` の平均（run ファイルごと） |
| 最近の試行の「走行秒」 | `run_sec` |
| ② 通し | 最初のスタートから最後のゴールまで（ホームでの付けかえもふくむ＝本番と同じ数え方）。試合の 150 秒と比べる |

- `run_sec` の無い古い記録（2026-10-03 より前）は時間の集計に入れない。`elapsed_sec` は残すが使わない。
- 誤差: 行が PC に届くまでの時間ぶん（Bluetooth）。0.1 秒前後の見こみで、実機ではまだ確かめていない（ハブの時計で測った値と 1 本比べて確かめる）。
- 複数ミッションの run では、`run_sec` はその 1 本全体の時間。ミッションごとの時間がほしいときは、run ファイルの区切りに `print("# M05")` のような行を足す必要がある（ハブ側の変更なので今回は入れていない）。

### 10.4 却下した案

| 案 | 却下理由 |
|----|---------|
| ハブの時計（StopWatch）で測って出す | いちばん正確だが、`setup.py` と全部の run ファイルを変えることになる。150 秒に対して 0.1 秒前後の誤差なら PC 側で足りる |
| `elapsed_sec` から決まった秒数を引く | ハブを探す・接続の時間は毎回ちがう（Bluetooth の具合）ので、引く量が決まらない |
| ログの各行の頭に時刻を付ける | `gyro_trace_summary.py`（行の頭の `T,`）など、ログを読む道具が読めなくなる |

## 11. 項目ごとの記録（2026-10-05）

M12 の「支柱 20 点」と「サポートタイ 10 点」のように、1 つのミッションに点の取れる項目がいくつもあるとき、
これまでは「成功（満点）／途中まで／失敗」しか記録できず、どの項目を取りこぼしたのかが残らなかった。
見こみ点も「成功＝満点・それ以外＝0 点」で、支柱だけ取れた本も 0 点に数えていた。
そこで、項目ごとに聞いて記録する（§9.4 で「入力の手間が大きい」と見送った「点数そのものを入れる」を、この形で入れる）。
決めたこと（オーナー 2026-10-05）:

| 項目 | 決めたこと |
|------|-----------|
| 聞き方 | 項目のあるミッションは **毎回すべての項目を聞く**（ミッションの「結果」は聞かず、項目から決める） |
| M07 の相手チームとのボーナス（10×2） | **記録しない**。M07 の成功は 20 点として数える（相手がいる試合でしか取れず、チームだけでは決まらない） |
| M04 | 1 問で **x / 1 / 2** と答える。x＝0 点（葉が取れなかった・キリギリスが生息地の外に出た）、1＝葉 1 枚 10 点、2＝2 枚目のボーナスまで 30 点。理由はメモに書く |
| 0 と個数・段階 | 個数と段階の項目も **x＝0**（`0` と打っても同じ）、数字＝個数・段階、`o`＝全部（いちばん上） |

### 11.1 項目の分け方

呼び名はルールブック日本語版の言葉にそろえる。定義は `scripts/bioglow_missions.py` の各ミッションの `parts`。

| 型 | ミッション（点） | 聞き方 |
|----|------------------|--------|
| 1 項目だけ | M07 菌糸体 20／M08 つる 30／M11 根のカバー 20／M13 キーストーン種 30 | いままでどおり「M08 の結果」を o / x / d で |
| 別々の項目 | M09 研究プラットフォーム・カメラトラップ・種子 各 10／M10 クモ・カタツムリ 各 10／**M12 支柱 20・サポートタイ 10**／M15 ひさし・天窓・コンポストハッチ・環境ボーナス 各 10 | 項目ごとに o / x |
| 基本＋ボーナス（「かつ」） | M01 ドローン 20＋LiDAR マップ 10／M03 調査フラグ 20＋岩 10 | 項目ごとに o / x。基本が x ならボーナスは聞かずに 0 |
| 段階 | M04 葉っぱ（0・10・30）／M05 根（0・一部 10・完全 20） | x / 1 / 2 |
| 個数 | M02 種子 0〜3（各 10）／M06 巣の中の葉っぱ 0〜4（各 10）／M14 再生ステーションの中の種子 0〜4（各 5）＋そのうちマットに接触 0〜その数（各 5） | x / 数字 / o（全部） |

- M15 の環境ボーナスは、ひさし・天窓・コンポストハッチのどれかが取れたときだけ聞く（ドックに何を置くかはチームが競技前に選ぶ・ルールブック p.7）。
- 記録できる満点は 440 点（ミッション 460 点から M07 の相手ボーナス 20 点を引いた分）。`/ 530` の表示は公式の満点のまま。

### 11.2 聞き方の例

```
run_coach_M12M02.py（M12 → M02）
   o=成功  x=失敗  d=途中まで  -=届かなかった ／ e=動かなかった  s=記録しない ／ b=1 つ前に戻る
   ぶぶんごとに聞くよ: o=とれた  x=とれなかった  すうじ=いくつ・どこまで ／ さいしょの質問で -=とどかなかった
M12 支柱は とれた？（20 点）[o] > o
M12 サポートタイは とれた？（10 点）[o] > x
M02 はなれた種子は いくつ？ 0〜3（1 つ 10 点）[3] > 2
メモ（なければ Enter・b=戻る）>

── この内容で記録します ──
 1  run_coach_M12M02.py（M12 → M02）  M12 20/30 点（支柱 ○・サポートタイ ×） / M02 20/30 点（はなれた種子 2）
```

- 既定値（Enter で入る値）は「全部取れた」（o・いちばん上の数）。`exit_code` が 0 でないときは最初の質問だけ `e`、セレクターでエラー行があったプログラムは x（0）。
- `b`（1 つ前に戻る）・最後の確認・番号で入れ直し・`e` / `s` は §9 と同じ。`-`（この run ではやらない・とどかなかった）は どの項目でも打てる（§11.8）。
- `scripts/trial_fix.py` でも同じ聞き方で入れ直せる。
- 質問の言葉は子どもも読むので、ひらがな多めの短い形（「〜は とれた？」「〜は いくつ？」）。項目の名前はルールブック日本語版の言葉のまま（2026-10-05）。子ども向けの説明は `README.md` のパターンC。

### 11.3 記録の形

`trials.csv` の右端に `part_results` 列を足す（見出しは最初に記録したときに自動で書きかわる）。

```
mission_results: M12=partial M02=partial
part_results:    M12.staff=1 M12.tie=0 M02.seeds=2
```

- 値は 1 / 0（取れた・取れない）、個数、段階。**点数は書かない**（ルールの更新で点が変わっても、点数表から計算し直せる）。
- 書くのは項目のあるミッション（§11.1 の「1 項目だけ」以外）で、届いたものだけ。
- `mission_results` は項目から自動で決める: 満点 → `success`、1 点でも取れた → `partial`、0 点 → `fail`。書き方は §9 のまま（古い版のスクリプトでも読める）。
- `part_results` が空の行（2026-10-05 より前）は、`success` なら全部取れた・`fail` なら全部 0・それ以外は「項目は分からない」として数える。行は書きかえない。

### 11.4 ダッシュボード

- **見こみ点 ＝ ミッションごとの「直近 3 回の平均点」の合計 ＋ 70（参考）**。1 項目だけのミッションは §5a と同じ値になる。
  例: M12 の直近 3 回が 支柱だけ・支柱だけ・0 点 なら (20 + 20 + 0) ÷ 3 ＝ 13 点。
- 点数マップの満点の列は記録できる満点（M07 は 20）。合計の前に「M07 相手チームとのボーナス（数えない）20」の行を出して、合計は 530 のまま。
- 項目が 2 つ以上のミッションは、点数マップのミッション名の下に項目ごとの直近 3 回を出す（`支柱 2/3 · サポートタイ 0/3`、個数は平均）。

### 11.8 1 つのミッションを別々の run でやる（2026-10-05）

M12 の支柱は run A、サポートタイは run B のように、1 つのミッションの項目を別々の run でやることがある。
それまでは、やらない項目も x（失敗）と答えるしかなく、見こみ点もミッション単位の平均だったので、
run A（20 点）と run B（10 点）が混ざって 15〜20 点になり、合わせて 30 点取れることが出なかった。決めたこと（オーナー 2026-10-05）:

| 項目 | 決めたこと |
|------|-----------|
| `-` | **どの項目でも打てる**。意味は「この run ではやらない・とどかなかった」。記録は `M12.tie=-`。全部の項目が `-` なら、ミッションごと「届かなかった」 |
| 既定値 | 前回の `-` は覚えない。**毎回 `-` を打つ**。前の項目で `-` を打っても、次の項目の既定値は o のまま（Enter で `-` が入ってしまわないように） |
| 1 本の結果 | **やった項目だけ**で決める。支柱だけの run で支柱が取れたら成功（`M12=success`） |
| 見こみ点 | **項目ごと**に「その項目に挑戦した直近 3 回」の平均点を出して足す。支柱は支柱をやった run、サポートタイはサポートタイをやった run から。1 項目だけのミッションは §11.4 と同じ |
| 安定 | 項目のあるミッションは、**どの項目も** 直近 10 回のうち 5 回以上挑戦して 80% 以上（満点）。まだ挑戦していない項目があると安定にならない |
| のびしろ | まだ挑戦していない項目は「サポートタイ（まだ記録なし・10 点）」と出る |
| ② 通し | 回の中の run を合わせて、項目ごとにいちばん良い点を足す（run A の支柱＋run B のサポートタイ＝30 点） |
| ボーナスの前提 | 前提の項目が `-`（別の run でやる）ならボーナスを聞く。x（0）のときだけ聞かずに 0。M14 のマットは、ステーションが `-` なら上限 4 |

却下した案: 前回 `-` にした項目を次の既定値にする（覚えないで毎回打つ・オーナー 2026-10-05）／run ファイルにその run でやる項目を書いておく
（決まりが 1 つ増える）／通しの最後にまとめて入れる（run ごとの出来が分からない）。
